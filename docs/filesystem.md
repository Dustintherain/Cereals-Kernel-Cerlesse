## 1. 概述

v0.7 文件系统阶段依赖 syscall/v0.6 的文件语义入口，以及内存子系统提供的分配/映射能力。

建议顺序（粗粒度）：

1. VFS 抽象先行：定义 `FileSystem` / `File` / `Directory` 语义、Inode、Mount。
2. RAMFS 作为第一版后端，接入 VFS。
3. 文件描述符表与 syscall 对接（open/read/write/close）。
4. 后续再补磁盘文件系统后端（FAT32）与 `mkfs` 工具。

非目标重申：不把具体文件系统写死进内核（ADR-004），VFS 抽象优先。

## 2. v0.7（VFS + RAMFS + ELF Loader 对接）

### 2.1 VFS 抽象

- VFS 抽象至少包含以下接口语义（具体 trait 签名在实现时定）：
  - `FileSystem`：挂载点语义、根目录/路径查找
  - `File`：读写/位置/元信息语义
  - `Directory`：目录遍历/子项语义
  - `Inode`：节点元信息语义
  - `Mount`：挂载管理语义
- VFS 的目的是在 syscall 层不依赖具体后端的前提下，提供统一的文件访问语义。

### 2.2 RAMFS

- 第一版后端是 RAMFS（内存中的文件系统）。
- 目录骨架计划：`/bin /dev /etc /home /proc /tmp /usr`（实际目录项在实现时定，必要时补增减）。
- RAMFS 的语义重点是：易于自测、无外部存储依赖、可在 v0.7 早期提供 VFS 验收基础。

### 2.3 ELF Loader 对接

- v0.7 中 ELF Loader 完整化后，才能加载更多用户程序；文件系统模块要能为 ELF Loader 提供可读取的文件语义。
- 因此 v0.7 里文件系统与 ELF Loader 是“并列扩展”的关系，二者都要为用户程序加载服务。

### 2.4 文件描述符表与 syscall 对接

- 文件描述符表在进程模型基础上建立（进程/线程模型见 process.md）。
- syscall 层通过文件描述符语义访问 VFS，而不是直接操作具体后端。

### 2.5 验收（v0.7）

- [ ] Shell 中可 `cd` / `ls` / `cat` RAMFS 内文件
- [ ] VFS 接口可在不改 syscall 层的前提下替换 FS 后端
- [ ] 文件描述符语义可用（至少串口/控制台设备层面先行，随后接入 RAMFS）
- [ ] ELF Loader 完整化后，用户程序可从 RAMFS 加载运行

## 3. 后续文件系统后端（v0.8 起，按需补）

### 3.1 FAT32

- FAT32 作为磁盘文件系统后端，挂载到 VFS（见 docs/drivers.md 的 v0.8 磁盘部分）。
- `mkfs` 工具（H-03，Python）负责生成 RAMFS/FAT 镜像（计划阶段）。

### 3.2 其他后端

- EXT2 及更多磁盘 FS 类型排在后续，非第一版目标。

## 4. 非目标 / 后续

- 完善的页缓存/写回/Consistency 策略：非第一版目标，必要时在实现阶段记录。
- 完整的权限/挂载语义（例如挂载选项、只读挂载、重解析点等）：视 v1.0 之前需求补充。
- 超大文件、高并发 IO、高性能目录索引：非第一版目标。

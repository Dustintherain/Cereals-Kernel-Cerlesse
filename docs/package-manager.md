# Cerlesse OS 包管理器设计（创新提案）

> 本文档是开发文档的一部分，用于记录对“高效、安全、轻量且具备类似 Windows 包管理器灵活性”的包管理方案的设想。
> 目前仍处于设计/评估阶段，不作为已落地的构建流程。

## 1. 目标与设计直觉

### 1.1 要解决的问题

一个操作系统级包管理器，尤其是自己造内核的项目，通常需要同时应对几类矛盾：

- **高效**：增量更新、并行下载/校验、尽量少的重复存储。
- **安全**：内容可验证、安装过程可控、不会因依赖更新导致系统回归崩坏。
- **轻量**：元数据与缓存不能膨胀成另一个“小系统”，管理器本身也不能太重。
- **灵活（类似 Windows 包管理器的体验）**：
  - 同时管理不同类型的包：系统组件、内核模块/驱动、用户态工具、开发工具、可选服务等。
  - 支持“查询/安装/卸载/更新/回退/修补”这种命令式体验，但不丧失声明式一致性。
  - 能处理“机器专属配置 + 共享原子更新”的混合形态，而不是非黑即白地走通用商店路线。

### 1.2 设计直觉

这里提出一个新颖但易于实现的方向：

> **声明式清单 + 追踪式安装区 + 阶段化事务的混合模型**

- 包的“意图”由声明式清单表达（想要哪些包、哪些版本约束、哪些渠道）。
- 实际安装结果由内核/主机追踪的“安装区”决定（系统区、共享区、用户区、映像区）。
- 安装/更新/回退是阶段化的事务：先准备、再验证、再使活，失败时可回滚。
- 元数据尽量按需拉取，不拍个巨型数据库住内存。

这种思路兼顾了：

- Windows 包管理器那种“我可以装任何东西、查任何东西、修任何东西”的灵活性。
- 操作系统内核项目更需要的可控性、最小化、可验证性。

## 2. 概念模型

### 2.1 核心术语

| 术语 | 含义 |
| ---- | ---- |
| **包（package）** | 一个可分发单元，可以是内核模块、驱动、用户态程序、库、工具、配置包等。 |
| **清单（manifest / intent）** | 声明要安装/保留的包集合，与具体文件位置解耦。 |
| **来源（source / channel）** | 包的提供方，可能是本地构建目录、网络仓库、UEFI/磁盘镜像附带区、项目内部仓库等；也可以是面向 Windows 风格商店体验的“可发现来源”，只要它能提供可验证的包修订。 |
| **安装区（install scope）** | 按生命周期与隔离级别划分的存储区域，例如：只读系统区、可升级共享区、机器私有区。 |
| **事务（transaction）** | 一次带验证与回滚能力的变更过程，不是直接原地改文件。 |
| **修订（revision）** | 包的一个可识别版本状态，由内容特征决定，而非单纯靠串行号。 |

### 2.2 分类视图（受 Windows 包管理器灵感，但不照搬）

一个灵活的包管理器，应该把“包”按**分布与更新语义**分类，而不只按“是应用还是库”分类。

建议的类别：

| 类别 | 典型内容 | 更新语义 |
| ---- | ---- | ---- |
| **系统组件** | 内核必须的模块、基础库、核心工具 | 严格、可回退、与系统一致 |
| **驱动/内核扩展** | 设备驱动、内核模块、平台适配层 | 可选、依赖内核接口版本 |
| **用户态工具** | CLI、实用程序、开发工具 | 较自由，可按用户/机器安装 |
| **服务/配件** | 守护进程、配置包、示例、脚本包 | 可选，可能带配置意见 |
| **映像捆绑包** | 出厂/镜像自带的只读内容 | 不管理为“可变安装”，而是作为基线 |

这样，命令体验可以很像 Windows 包管理器——装任何东西、查任何东西、修任何东西——但底层仍能做到轻量和可控。

## 3. 创新点：不用“全量依赖数据库”的意图驱动模型

传统包管理常依赖一套全局数据库，记录所有已安装包、所有元数据、所有依赖关系。这对内核项目来说往往过重。

本文提出的替代方案是：

### 3.1 意图优先

- 用户/系统声明“我想要什么”，而不是先追踪“当前安装了什么大数据库”。
- 管理器把意图翻译成事务任务，而不是先拉全量元数据再凭空决策。

### 3.2 追踪优先于枚举

- 不预先枚举全局状态，而是沿着“安装区”追踪真实交付物。
- 查询时可以按需拼接可观测信息，而不是维护一个巨大的可安装清单数据库。

### 3.3 按需获取元数据

- 元数据可以按包、按来源、按事务阶段拉取。
- 默认不把完整描述数据库常驻内存或磁盘。

这能带来两个好处：

- **轻量**：元数据粒度可控，不漂移成独立的重型服务。
- **灵活**：添加新的来源、类别、安装区，不需要重写一套中心数据库模型。

## 4. 安全模型

### 4.1 内容可验证

每一个分发单元都应该能回答：**这是我所期望的那个包吗？**

建议做法：

- 每个包修订由**内容导出来识别**，而不仅仅靠版本号。
- 分发时附带可验证的一致性信息，校验失败的包不进入“激活”状态。
- 安装区中的“已准备但未激活”内容不被当作生效状态。

### 4.2 域间边界

包管理器不应允许随意混淆不同安全域：

- **内核级内容**与**用户态内容**分开描述与分开交付语义。
- **系统区**与**用户区**在安装评估与回退策略上不同。
- 可以“装很多东西”，但不能模糊哪些是机器共享、哪些是用户私有、哪些是系统基线。

### 4.3 事务与回退

安装/更新应具备：

- **准备阶段**：下载/定位内容、做完整性检查、生成候选结果。
- **验证阶段**：检查依赖意图、冲突、目标区容量或策略约束。
- **激活阶段**：使变更生效。
- **回退阶段**：激活失败或验证失败时，尽量恢复到已知稳定状态。

这样即使灵活性很高（可以装很多不同类型的包），也不会变成“乱装乱改不可控”。

## 5. 轻量性设计

### 5.1 不维护全局大库

- 元数据按需获取。
- 已安装状态由安装区追踪，而非靠巨型注册表或数据库。
- 缓存可限制、可清理、可按渠道独立管理。

### 5.2 最小管理器本体

管理器本身应尽可能由少量核心能力组成：

- 解析意图
- 定位/获取包修订
- 校验内容
- 编排事务
- 记录可观测结果

不必一开始就做成图形化商店、权限管理大脑、系统设置中心等。

### 5.3 增量与共享

- 相同内容尽量只存一份。
- 不同包表达式相同的部分，不重复存储。
- 更新以增量准备为主，而非每次全量重建。

## 6. 灵活性设计（Windows 式体验的操作系统适配）

### 6.1 查询与搜索体验

可以提供类似的命令式查询能力：

- 查已安装
- 查可获取的包
- 查包的类别、来源、适用环境
- 查哪些东西属于系统基线，哪些是后加的

### 6.2 安装与卸载的灵活性

支持多种安装意图：

- 安装指定包
- 安装一组包
- 安装某个来源中的包
- 仅安装到某一安装区（例如用户态工具可仅装给当前用户，系统组件则走系统区）
- 卸载指定包/修订
- 回退到先前修订

但灵活性不等于无秩序：不同安装意图仍映射到不同的安全语义与事务检查。

### 6.3 修补与局部更新

对系统维护很重要的能力：

- 不只整包替换，也可以有“修补/增量更新”的表达。
- 对内核模块/驱动，可支持“先准备、新验证、再选择性激活”的节奏。
- 对用户态工具，可支持更快的局部替换。

### 6.4 多来源共存

可以同时存在：

- 内建/镜像来源
- 本地开发构建来源
- 项目内部来源
- 外部来源（如适用）

管理器不应强迫所有内容都走同一个入口。类似 Windows 包管理器的灵活性就体现在这里：**不管它是系统自带的、后来装的、开发版的、还是自动更新来的，都能统一检索与管理。**与此同时，不同来源的内容仍保留各自的元数据与校验方式，避免把灵活性变成模糊性。

这一层灵活性还可以延伸到使用习惯上：用户既可以一条命令装一个工具，也可以通过清单持续维持一套期望状态；既可以按功能领域挑语言和包的组合——例如内核周边用 Rust 核心、AI/科学计算类任务用 Python 胶水、共享部件用可验证包修订——也不迫使所有内容在同一套模型里硬写。

## 7. 提案架构（初步）

### 7.1 高层角色

```text
意图层（清单/命令）
   ↓
规划器（事务任务生成、冲突/依赖意图审查、目标区分配）
   ↓
获取与校验层（来源拉取、内容识别、完整性检查）
   ↓
安装区层（系统区/共享区/用户区/映像基线）
   ↓
激活与回退管理（生效、观测、回滚）
```

### 7.2 工作流示例

1. 用户通过命令或清单表达意图。
2. 规划器决定需要哪些包修订、从哪个来源、准备到哪个安装区。
3. 获取层拉取/定位内容并做完整性验证。
4. 事务准备完成后，再激活。
5. 如果激活失败，回退到稳定状态；如果只是查询，什么都不写。

### 7.3 状态观测

管理器应该能回答：

- 当前有效的意图是什么
- 哪些包修订已激活
- 哪些内容已准备但未激活
- 哪些是系统基线/映像捆绑内容
- 哪些安装区正在被使用
- 哪些保存区/缓存正在被使用

这些信息用于排障、回退和审计，而不是为了构造一个巨型中心数据库。

## 8. 与本项目的关系

### 8.1 现在的定位

Cerlesse 当前是 Rust 内核项目：
- 内核核心用 Rust。
- 主机侧工具使用 Python / Go。
- 目前的交付与验证路径以 boot/kernel 构建、QEMU 测试为主。
- 语言选型方面，已有辅助文档 docs/lang-selection.md 按功能领域汇总了性能最佳语言的参考，包管理器设计可以顺着这个思路继续延伸——不是让包管理器取代语言选型，而是让选型后的组件在分发与更新上更灵活、更安全、更轻量。

所以这个包管理器目前应被视为**面向未来的设计文档**，不是立即替换当前构建/安装流程的方案。

### 8.2 可能的接入方式

- 可先作为**主机侧工具链的一部分**来设计原型。
- 内核态需要的“包/模块/驱动加载语义”可以后续再从操作系统角度补充。
- 在 v0.7/v0.8/v0.9 引入用户态程序、驱动、网络服务等概念时，可以逐渐对齐包管理器的分类与事务语义。

## 9. 与当前开发阶段的契合

### 9.1 当前阶段小结

当前进度（由 DEVELOPMENT.md 和各阶段文档确定）大致如下：

- **已完成**：v0.1 Bootloader + Kernel 进入、串口输出；v0.2 GDT/IDT/异常；v0.3 物理/虚拟内存 + 内核堆。
- **下一步重点**：中断控制器、时钟、键盘等底层设施，以及后续的进程/调度/syscall/VFS/驱动/网络等环节仍在规划中。
- **文档状态**：已有按阶段组织的文档骨架，部分主题文档待未来阶段填充。

### 9.2 包管理器在这个节奏里的位置

- 短期不应干扰内存、中断、进程、syscall、VFS这条主线。
- 但可以在主线推进的同时，把包管理器作为“系统周边工具/主机侧能力”先定义清楚。
- 尤其当项目开始涉及“内核模块、驱动、可选用户态组件、工具链更新”时，这个包管理器思路就能派上用场。

## 10. 验收思路（将来）

可能的验收方向：

- 管理器能描述多种包类别与安装区。
- 管理器能按需获取元数据，不依赖巨型全局数据库。
- 事务具备准备/验证/激活/回退阶段。
- 内容修订可验证，安装结果可观测。
- 命令体验对用户来说具有足够的灵活性（查、装、卸、修、回退、多来源共存）。
- 主机侧原型不显著增加内核主线复杂度。
